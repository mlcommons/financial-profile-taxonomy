# MLCommons Agent Reliability Profile Taxonomy

[![License: CC BY 4.0](https://img.shields.io/badge/License-CC_BY_4.0-lightgrey.svg)](https://creativecommons.org/licenses/by/4.0/) [![Version](https://img.shields.io/badge/version-0.1.0-blue.svg)](CHANGELOG.md) [![Status](https://img.shields.io/badge/status-draft%20for%20comment-orange.svg)](#status) [![Contributions Welcome](https://img.shields.io/badge/contributions-welcome-brightgreen.svg)](CONTRIBUTING.md)

A shared, machine-readable vocabulary for stating what a deployed AI agent is permitted to do, how autonomously, in what context, and with what containment, developed by the [MLCommons Financial Services Working Group](https://mlcommons.org/).

The Agent Reliability Profile supports one bounded, falsifiable claim:

> **This agentic system reliably functions within its operating boundary.**

The operating boundary has four axes: **autonomy tier**, **operational design domain**, **action classes**, and **control envelope**. This repository publishes the full option universe for each axis, so that two institutions describing the same deployment produce the same description.

**This taxonomy is a vocabulary, not a certification.** MLCommons does not assess, certify, or rank deployments through this repository. Publishing the taxonomy does not imply that any deployment described in its terms has been tested.

## Key Concepts

### The Deployment Is the Unit of Analysis

A Profile describes a **deployed agentic system**, not a vendor, product, or model release. The same product holding production credentials is a different risk object from that product running read-only in a sandbox. The deployment identity includes the model and version, the harness and its policy configuration, the tool catalog (including MCP servers), the credential and role configuration, the operating environment, the accountable owner, and the time at which the configuration was in force.

### A Bounded, Falsifiable Claim

Fixing the four axes converts the open question "is this agent reliable?" into a scoped assertion. Formally, the scope of deployment *D* is the tuple

```
S(D) = (T, O, A+, A-, C)
```

and every component determines a test that can fail:

| Axis | The claim fails if... |
|---|---|
| Autonomy tier (T) | approval logs show reflexive acceptance |
| Operational design domain (O) | the agent proceeds after leaving its domain |
| Action classes (A+ / A-) | entitlements permit classes outside A+ |
| Control envelope (C) | a named control is documented but absent from the running configuration |

The claim is bounded in time, expires on boundary crossing, and jointly fixes the test environment, the evaluator suite, the failure thresholds, and the wording of the claim.

### Axis > Group > Value

Each axis is organized as a small hierarchy. **Axes** capture the four properties every deploying institution already recognizes: how much the system does on its own, where it may work, what it may do, and what contains it. **Groups** subdivide by a single explicit rule (autonomy tiers vs. modifiers; lines of business; control layers). **Values** are the atomic units with canonical IDs (`T2`, `ODD.30`, `A9`, `harness.kill_switch`) that Profiles, tools, and supervisory analysis can reference.

### The Taxonomy Standardizes the Schema, Not the Instances

The taxonomy is the **public option universe**. A Profile is a **private instance**: one institution's values for one deployment, with its own evidence. The operational design domain in particular admits standardization of its schema only; instances are built one at a time by the institutions developing agents. Publishing the taxonomy reveals nothing about any institution's deployments.

### Design Requirements

The taxonomy is built to satisfy the nine requirements set out in the preprint (Section 2.3):

1. **Specificity**: identify a deployment and the exact conditions the claim covers
2. **Comparability of description**: two institutions describe functionally similar deployments in the same vocabulary
3. **Risk-based assurance**: low-cost inventory coverage, higher-cost assurance for higher-risk deployments
4. **Evidence traceability**: field values and evaluated runs can be reconstructed from sources and traces
5. **Machine readability**: support inventories, change detection, policy checks, and supervisory analysis
6. **Cryptographic integrity**: bind the issued artifact to issuer, subject, evidence hashes, method version, and validity period
7. **Change sensitivity**: distinguish changes that void a Profile, require partial retesting, or have no effect
8. **Software neutrality**: admit conforming implementations from institutions, assurance firms, vendors, and open-source projects
9. **Compositionality**: a platform can carry an enforcement-claim Profile inherited by reference by the agents hosted on it

## How to Use This Taxonomy

**Financial institutions**: Use the four axes to inventory your agentic estate in one vocabulary. Start with the [taxonomy overview](taxonomy/taxonomy-overview.md), then the axis pages. The [worked examples](taxonomy/examples-overview.md) show complete bounded claims for a coding agent and a financial-crime alert-triage agent.

**Supervisors and standards bodies**: Reference axis values by canonical ID when specifying expectations, comparing deployments across firms, or identifying outliers. The [crosswalk](taxonomy/crosswalk.md) maps each axis to existing frameworks.

**Assurance firms and tool builders**: [`taxonomy.yaml`](taxonomy/taxonomy.yaml) is the machine-readable source. Build against canonical IDs, not display names. The same IDs are used by the Agent Reliability Profile Kit; `scripts/export_vocab.py` writes the taxonomy in the Kit's vocabulary format.

**Contributors**: See [CONTRIBUTING.md](CONTRIBUTING.md) to propose a new use case, a new control, a crosswalk mapping, a worked example, or a structural change.

## Relationship to the Profile Kit

This repository is the source of truth for the four axes: IDs, labels, and definitions. The [Agent Reliability Profile Kit](https://github.com/mlcommons/agent-reliability-profile-kit) (specification, conformance suite, and reference tools) consumes them as JSON vocabularies; its `COMPATIBILITY.md` states which taxonomy release each Kit release pins. `scripts/export_vocab.py` writes those files to [`vocab/`](vocab/); a Kit release pins a tagged taxonomy version and copies them. The Profile artifact itself (sections, provenance, assurance levels, conformance rules) is specified in the Kit's specification, which governs; this repository's Profile pages are explanatory summaries, and [`profile.yaml`](taxonomy/profile.yaml) records which vocabularies each repository owns. Proposals to change the Profile rules go to the Kit.

## Status

Version 0.1.0 is a **draft for comment**, corresponding to Phase 1 of the implementation program ("agree on the vocabulary"). The success criterion for that phase is that two institutions describe the same deployment in the same words, tested through inter-rater classification of shared example deployments. We expect robust discussion, not immediate agreement, and expect pilot feedback to revise the axes and their values.

## Versioning

The taxonomy uses semantic versioning:

- **Major** (e.g., 1.0 → 2.0): an axis is added, removed, or fundamentally restructured (e.g., a change to the tier scale or to the action-class ordering principle)
- **Minor** (e.g., 1.0 → 1.1): new values are added (use cases, controls, multiplying-factor values, modifiers), existing values are refined, or worked examples are added
- **Patch** (e.g., 1.0.0 → 1.0.1): documentation fixes, example updates, metadata corrections

See [CHANGELOG.md](CHANGELOG.md) for version history.
